# Adopting the 0.1 packages

This note is for operators moving onto the first release of these packages,
`0.1^20251202git463382b-1`, either on a fresh host or from guildmaster built
and installed from upstream's sources. Everything below is covered in more
detail in the [users' guide](../users-guide.md).

## What changes compared with an upstream install

Upstream's Meson build installs its executables under `/usr/local` by
default, and a minimal unit and udev rule into systemd's and udev's
directories. The packages differ deliberately.

| Aspect | Upstream build at `463382b` | These packages |
| --- | --- | --- |
| Executables | under the Meson prefix, `/usr/local/bin` by default | `/usr/bin/guildmaster`, `/usr/bin/gm-run` |
| Service account | root | the unprivileged `guildmaster` system account |
| Unit | runs as root, no options, no sandboxing | hardened `guildmaster.service`, disabled until enabled |
| `/dev/guild` | world-writable (`MODE="0666"`) | `root:guild`, mode `0660`; clients join `guild` |
| `/dev/cuse` | root only | `root:guildmaster`, mode `0660` |
| Capacity | online processors plus one, fixed | the same by default; `--tokens N` selects another |
| Configuration | edit the unit | `/etc/sysconfig/guildmaster`, kept across upgrades |
| `cuse` module | loaded by hand or at boot | loaded on demand when the service starts |

_Table 1: an upstream install compared with the packages._

Clients that relied on the world-writable device lose access until their
users are added to the `guild` group. That is intended.

## Moving from an upstream install

1. Stop and disable the upstream service, and let running builds finish
   first, because stopping it removes `/dev/guild`.
2. Remove what the upstream install put in place. Its executables are in
   the Meson prefix, `/usr/local/bin` unless another was chosen. Its unit and
   udev rule go wherever the `systemd` and `udev` pkg-config files point,
   normally `/usr/lib/systemd/system/guildmaster.service` and
   `/usr/lib/udev/rules.d/cuse-guild.rules`. Remove the rule in particular:
   it would keep `/dev/guild` world-writable. Remove the upstream unit too:
   the package installs its own at the same path, and RPM replaces an
   unowned file there without warning. Then run
   `sudo systemctl daemon-reload` and `sudo udevadm control --reload`.
3. Install `kernel-modules-extra` for the running kernel and the package, as
   the users' guide describes. Installing the package applies its udev rule
   to an existing `/dev/cuse` straight away.
4. Choose the capacity in `/etc/sysconfig/guildmaster`, for example
   `GUILDMASTER_OPTS="--tokens=2"`, rather than editing the unit.
5. Add each user who runs builds to `guild`; they must log in again.
6. `sudo systemctl enable --now guildmaster.service`, and check it with
   `systemctl show guildmaster.service --property ActiveState,SubState,Result`.

`gm-run` behaves as upstream's: it takes one token, appends
`--jobserver-auth=fifo:/dev/guild` to `MAKEFLAGS`, and returns the token when
the command exits.

## Upgrades and restarts from now on

Package upgrades never restart a running daemon and never replace
`/etc/sysconfig/guildmaster`. A restart creates a new token pool and strands
clients holding the old device, so drain first, then restart; the users'
guide gives the procedure. The package provides no metrics interface: the
journal and `systemctl show` are the observability it offers.

Installing guildmaster does not by itself constrain Cargo or any other tool,
and a token count is not a limit on threads or memory.
